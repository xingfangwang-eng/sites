Usage

                    
Initialize the generated guarded wrapper in your project as follows:

                    
                    
1. Import in Project

                    
// Save generated code as api-guard.js
import { createGuardedApi } from './api-guard.js';

// Initialize guarded API client
const api = createGuardedApi();


                    
2. Basic Usage

                    
// Use the wrapped API
async function fetchData() {
  try {
    const result = await api.fetch('https://api.example.com/data');
    console.log('Success:', result);
    return result;
  } catch (error) {
    console.error('Request failed:', error.message);
    throw error;
  }
}

// Call the function
fetchData();


                    
3. Custom Configuration

                    
// Customize retry count, timeout, etc.
const customApi = createGuardedApi({
  maxRetries: 5,
  timeout: 10000,
  failureThreshold: 3
});

What is Circuit Breaker Pattern?

                
The Circuit Breaker pattern is a software design pattern that stops requests to failing services when continuous failures are detected, preventing cascading failures.

                
In frontend applications, the circuit breaker (implemented using the createCircuitBreaker factory function) prevents:

                
    
                    
  • Server overload from excessive retry attempts
    • 
                    
  • UI freezes while waiting for unresponsive requests
    • 
                    
  • Memory leaks from hanging requests
    • 
                

                
The circuit breaker has three states: CLOSED (normal operation), OPEN (tripped, rejecting requests), and HALF_OPEN (testing recovery). When consecutive failures reach the threshold, it switches from CLOSED to OPEN. After a cooldown period, it enters HALF_OPEN to allow a test request.

            


            

                
Why is Simple Retry Dangerous?

                
Many developers use simple fixed-interval retry strategies, such as retrying every 1 second. However, this approach poses serious risks in production:

                
Retry Storm: When a service experiences a transient failure, all clients retry simultaneously. With fixed intervals, retry timestamps overlap across multiple rounds, causing an instant flood of requests that overwhelms the server and may trigger secondary failures.

                
Exponential Backoff is a better solution: Wait time doubles with each retry (1s → 2s → 4s → 8s). This approach:

                
    
                    
  • Spreads retry timestamps to reduce server load
    • 
                    
  • Provides recovery time for temporarily failing services
    • 
                    
  • Calculates backoff using Math.pow(2, attempt - 1) * 1000
    •
